# reBot Arm DLI Isaac Sim

An Isaac Sim teleoperation and data-collection project for the Seeed Studio
reBot Arm B601-RS. It adapts NVIDIA's SO-101 Sim-to-Real workflow to a
stationery-sorting task: use a physical reBot Arm 102 Leader to place two pens
and one eraser into a fixed pencil cup.
![overview](./media/overview.gif)
The default application contains no autonomous arm trajectory. The simulated
B601 follows the leader's six arm joints and gripper command, and holds its
last target whenever leader data is unavailable.

> 📖 **Isaac Sim 6.1 数据采集教程（中文）: [TUTORIAL_zh.md](TUTORIAL_zh.md)** —
> 完整的安装、环境配置、采集、可视化与无硬件验证流程。

## Features

- Real-to-Sim control from a reBot Arm 102 Leader at 60 Hz
- 120 Hz Isaac Sim physics and control loop
- Direct arm-joint mirroring for low-latency response
- Gravity-resistant, low-force dual-finger gripper control based on
  [Seeed PR #21](https://github.com/Seeed-Projects/reBot-Isaacsim/pull/21)
- High-friction thin-object contact and configurable near-field grasp assist
- Two recorded cameras: wrist-mounted `front` and overhead `external`
- One unrecorded, freely adjustable Isaac Sim debug viewport
- Domain randomization for object poses, masses, and lighting
- LeRobot Dataset v3 recording with `front` and `side` images
- Portable, project-local USD assets

## Task

The default scene is the **vial variant**: three opaque vials (SO-101
workshop assets, Ø34 × 116 mm) and one fixed vial rack with four Ø32 slots,
centred in front of the robot (slot centres at `(-0.190, 0.090)`,
`(-0.190, 0.150)`, `(-0.130, 0.090)` and `(-0.130, 0.150) m`).

A second, optional **stationery variant** keeps the original task: two pens
and one eraser (Poly Haven stationery set) placed into a fixed pencil cup.
Both variants share the same robot, workspace, and camera rig; select one at
launch:

```bash
./run.sh --variant vials        # default: three vials into the vial rack
./run.sh --variant stationery   # two pens + eraser into the pencil cup
```

The stationery variant writes its dataset to
`datasets/rebot_stationery_pencil_cup` with the task text
`Put the two pens and the eraser into the pencil cup`, and builds its scene
on first launch (`scenes/rebot_stationery_pencil_cup.usda`).

Press `R` to reset the objects. They are spawned above separate areas of the
workspace and fall onto the work surface under gravity. Use the leader arm to
stand each vial in a slot. Both assets keep their own materials; the vial has
a blue cap and the rack is orange.

## SO-ARM101 variant (white, real+sim linked teleoperation)

A third, fully separate application swaps the robot while keeping the
original box and props: the NVIDIA [Sim-to-Real SO-101
Workshop](https://github.com/isaac-sim/Sim-to-Real-SO-101-Workshop)'s
`SO-ARM101` USD (copied to `assets/so101/`, Apache-2.0) is referenced at
`/World/Robot` and painted **white** by re-authoring its printed-parts
material, with the STS3215 servo bodies kept dark like a real white kit.
The enclosure, table, vial rack, vials, lighting, and overhead/side cameras
are generated by the same functions as the reBot scene; only the robot and
the wrist camera rig differs: it replicates the workshop's own
gripper-camera pose (gripper-local offset `(-0.005, 0.06, -0.062)` with
an Euler `-45, 0, 0` rotation, verbatim, so the view tracks the gripper
exactly like the workshop's camera in every arm pose). The
The base sits at `(-0.021, 0.46) m`: centred on the enclosure's
left-right midline (the USD's base plate is offset ~2 cm right of its
origin) and far enough forward that the folded init pose's raised upper
arm only nominally grazes the enclosure's open-side interior line at
`0.535 m` (1.7 mm, invisible on the open side).  Relative to the
reBot layout, the vial rack and the vials are swapped left/right and moved
10 cm toward the robot, putting every slot and spawn point within the
SO-101's ~0.38 m reach.

Launch it with `run_so101.sh`; it never reads or writes the reBot scenes,
configs, or scripts:

```bash
./run_so101.sh --leader-port /dev/ttyUSB0
```

- **SO-101 leader required** (`so101_leader`, Feetech STS3215). Calibrate it
  in the LeRobot venv with `lerobot-calibrate --teleop.type=so101_leader
  --teleop.port=... --teleop.id=so101_leader` (see the workshop's chapter 7).
  The venv additionally needs the Feetech SDK:
  `uv pip install feetech-servo-sdk` (the reBot-only install list omits it).
- Joint mapping follows NVIDIA's official `lerobot_interface.py` table: the
  five leader joints map onto `Rotation/Pitch/Elbow/Wrist_Pitch/Wrist_Roll`
  and the gripper onto the `Jaw` (−10..100°), with no additional offsets.
- `S/C/R` recording keys, domain randomization, watchdog hold, and the
  `front`+`external` 30 FPS camera pair work exactly as in the reBot app.
- Scripted end-to-end pipeline check without any hardware:
  `./run_so101.sh --headless --auto-record 2` records two mock-leader
  episodes into the real dataset root (verified: 2x166 frames, replay via
  `scripts/replay_episode_so101.py`, and ACT training with
  `lerobot-train --policy.type=act --policy.push_to_hub=false ...`).
- Cartesian keyboard teleoperation: press `Y` in the viewport and drive
  the END EFFECTOR directly — `W/S/A/D` forward/back/left/right, arrows
  up/down, `Q/E` wrist roll, `F` jaw toggle, `B` 5/15 mm steps, `T`
  records (S is backward in this mode).  The forward kinematics are
  extracted from the USD joint frames (validated to 0.1 mm against the
  physics at startup) and each step is solved with damped least squares
  over the four arm joints while holding the tool tilt.  Usable without
  any leader via `--no-start-bridge`; the grasp assist and recording
  stay intact.
- A reBot-style near-field grasp assist attaches the nearest vial when the
  leader closes the gripper inside the finger corridor and carries it
  stress-free (`[GRASP]`/`[RELEASE]` in the terminal); the scene also caps
  the jaw closing speed, adds finger friction, and damps the vials so
  pure-contact grasps no longer squeeze vials out of the fingers.

### Real + simulated arm linkage

Connect the real **SO-101 follower** on a second port to teleoperate both
arms with one leader — the bridge drives the real follower and streams its
*measured* joints to the simulation, so the white sim arm mirrors the real
arm (this mirrors the workshop's
[chapter 8](https://docs.nvidia.com/learning/physical-ai/sim-to-real-so-101/latest/08-operating-so101.html)
workflow, extended with a sim twin):

```bash
./run_so101.sh --leader-port /dev/ttyUSB0 --follower-port /dev/ttyUSB1
```

The follower must already be calibrated
(`lerobot-calibrate --robot.type=so101_follower ...`); start both arms in
similar poses, as the workshop advises. Use `--no-follower` for sim-only
teleoperation (the sim then mirrors the leader directly), and watch the
status line's `src=LEADER|FOLLOWER` field to confirm which measurements the
simulation is following.

The dataset is written to `datasets/so101_vials_front_side` with the
six-joint SO-101 feature space (`shoulder_pan/shoulder_lift/elbow_flex/
wrist_flex/wrist_roll/gripper` in lerobot raw units), the same space as real
SO-101 datasets, so simulated episodes can mix with real ones for policy
training. Offline regression and camera validation:

```bash
./run_so101.sh --test                  # mock-leader joint tracking
./run_so101.sh --test --test-recording # + cameras, H.264, LeRobot dataset
```

Headless stills of the white robot in the enclosure:
`"$ISAACSIM_ROOT/python.sh" scripts/capture_so101_previews.py`
(writes `media/so101_camera_previews/`).

## Requirements

> ⚠️ **Use an NVIDIA RTX GPU with at least 12 GB of VRAM.** With 8 GB
> (e.g. 8 GB laptop GPUs) the scene's render load can starve the desktop
> compositor and freeze the whole machine within minutes — this was
> reproduced twice during development, with the built-in mitigations and
> `--single-viewport` enabled. See `TUTORIAL_zh.md` §1 and §10.

- Ubuntu with a working NVIDIA GPU (≥ 12 GB VRAM recommended; 8 GB risks a
  desktop freeze) and Isaac Sim 6.1
- Launch isaacsim from `~/isaacsim` by default, `ISAACSIM_ROOT` set to a
  different installation directory
- `git-lfs` installed before cloning (the robot, workspace, and stationery USD
  assets are stored with Git LFS; without it only pointer files are downloaded)
- A reBot Arm 102 Leader connected through USB-UART

## Leader calibration

The default calibration ID is `rebot_arm_102_leader`. To recalibrate, place the
leader in the zero pose required by Seeed's guide and fully close the gripper:

```bash
cd ~/rebot_lerobot
source .venv/bin/activate

lerobot-calibrate \
  --teleop.type=rebot_arm_102_leader \
  --teleop.port=/dev/ttyUSB0 \
  --teleop.id=rebot_arm_102_leader
```

For temporary serial-port access:

```bash
sudo chmod 666 /dev/ttyUSB0
```

For persistent access, add the current user to `dialout`, then log out and back
in:

```bash
sudo usermod -aG dialout "$USER"
```

References:

- [Seeed leader calibration guide](https://wiki.seeedstudio.com/rebot_arm_b601_rs_lerobot/#calibrate-the-leader-arm)
- [Seeed reBot Isaac Sim guide](https://wiki.seeedstudio.com/rebot_arm_b601_rs_isaacsim/)

## Quick start

Connect the leader, then run:

```bash
cd ~/rebot-arm-dli-isaacsim
./run.sh --leader-port /dev/ttyUSB0
```

If only one `/dev/ttyUSB*` device is present, automatic detection is normally sufficient:

```bash
./run.sh
```

To use another Isaac Sim installation:

```bash
ISAACSIM_ROOT=/path/to/isaacsim ./run.sh
```

Do not run another process that uses the same serial port or UDP port. The launcher starts a separate LeRobot Python process and sends leader state to
`udp://127.0.0.1:5005`.

### Keyboard controls

| Key | Action |
| --- | --- |
| `R` | Reset all three objects and apply domain randomization |
| `S` | Start or stop one recorded episode |
| `C` | Cancel the current episode without saving it |

The Isaac Sim viewport must have keyboard focus. Closing Isaac Sim or pressing
`Ctrl+C` also shuts down the leader serial process.

## Workspace layout

The scene uses `assets/workspace/box.usdz` as a self-contained enclosure. Its
opening faces world `+Y`; the robot tail faces the opening and its working
direction points into the enclosure. The robot base is offset 5 cm inward from
the opening edge. Two 4000 K light strips illuminate the workspace from above,
and the enclosure sits on a wooden table with static collision geometry.

The pencil cup is fixed at `(x=-0.16, y=0.12) m`. The stationery items are
independent dynamic rigid bodies.

## Gripper and grasp behavior

Move the gripper close to an object and close the leader gripper. The default
near-field grasp assist selects the nearest pen or eraser using a finite
cylinder or oriented-box surface approximation. Attachment is permitted only
when the gripper closes and the object surface is within `0.040 m` of a sampled
`0.090 m` corridor running from the finger roots toward the fingertips. This
volume tolerates small CAD and fingertip calibration errors without extending
sideways across the workspace. Opening the leader gripper releases the object.

The assist only stabilizes human demonstrations; it never moves the arm by
itself. It preserves the object's measured pose relative to the wrist, filters
only current object-to-finger contacts while attached, clears residual release
velocity, and restores contact after the fingers separate.

Physical contact is configured as follows:

- finger static/dynamic friction: `2.4 / 2.0`;
- stationery static/dynamic friction: `1.8 / 1.5`;
- maximum friction combination and improved patch friction;
- stationery contact offset: `0.002 m`;
- stationery rest offset: `0 m`;
- torsional friction patch radius: `0.002 m`;
- zero restitution;
- object maximum depenetration velocity: `0.25 m/s`;
- object maximum contact impulse: `0.05 N·s`.

The gripper uses two explicit linear drives with a shared 1:1 target:

- stroke: `0.0500 m`;
- stiffness: `1200 N/m`;
- damping: `30 N·s/m`;
- maximum force: `12 N`;
- maximum speed: `0.08 m/s`.

The contact lock activates in the `0.022 m` closing band and prevents the
fingers from driving through a nearby object. Look for `[CONTACT-LOCK]` and
`[GRASP]` in the terminal when a grasp succeeds. If a thin object does not
produce enough physical drive lag for the primary detector, a fallback can
activate only after the measured finger opening is below `0.028 m` and the
object is already inside the grasp corridor. It prints
`[CONTACT-LOCK-FALLBACK]` before `[GRASP]`.

The one-second teleoperation status line reports `gripper_cmd`,
`gripper_actual`, `nearest`, `distance`, `lock`, and `attached`. These fields
make it possible to distinguish leader mapping, physical finger motion,
near-field selection, and attachment failures directly from the terminal.

To disable grasp assist and use only PhysX contact and friction:

```bash
./run.sh --leader-port /dev/ttyUSB0 --strict-physics
```

## Cameras

The GUI exposes four views:

1. the default adjustable Isaac Sim viewport, used only for debugging;
2. `front`, mounted on the wrist and recorded;
3. `side`, fixed inside the enclosure, shown for reference but not recorded;
4. `external`, the overhead data-collection camera, recorded.

The recorded cameras run at `640x480`, 30 FPS. Both `front` and `external`
therefore use the dataset image shape `[480, 640, 3]` (height, width, RGB).

- `front`: `/World/Robot/link6/UVC32Mount/UVC32Camera/FrontCamera`
- `side`: `/World/Cameras/Side`
- `external`: `/World/Cameras/External`

The side camera is located at `[0.37, -0.05, 0.60] m` and points toward
`[0.00, 0.25, 0.16] m`. It uses a `9.5 mm` wide-angle focal length. It is
shown for reference only; the recorded pair is `front` + `external`.

The external camera stands on the work surface on the
`data-collection-camera-mount-v2` frame: centred in X, its 590 mm mast behind
the wrist, with the camera itself at `[0.00, 0.235, 0.586] m` looking straight
down. Its visuals are render-only, and it is one of the two recorded streams.
To record the fixed `side` view instead, swap the camera names in
`CAMERA_NAMES` (`scripts/episode_recorder.py`, `scripts/dataset_writer.py`)
and in `_capture_record_frame` (`scripts/leader_teleop.py`).

The wrist camera uses a converted version of Seeed's UVC32 mount, placed from
Seeed's own wrist-camera assembly, so the bracket's clamp sits on the wrist
axis and the camera looks along the board's plate normal. The camera's pose and
field of view are derived from the modelled lens, and its visuals have no mass
or collision, so they do not affect robot dynamics.

Use `--single-viewport` to hide the two floating camera windows while keeping
both recording streams active.

## Domain randomization

At startup and after pressing `R`, the application randomizes:

- stationery XY position, yaw, and mass;
- dome and key-light intensity and color.

The pencil cup, enclosure, and both cameras remain fixed. The wrist camera sits
at the front of the modelled UVC32 lens and looks along its axis, so the
recorded view matches the camera model exactly; widen `position_jitter_m`,
`target_jitter_m` or `focal_length_mm` under `front_camera` in
`config/domain_randomization.json` to randomize it again. Configuration lives in
`config/domain_randomization.json`.

Run a fixed scene with:

```bash
./run.sh --leader-port /dev/ttyUSB0 --no-dr
```

## Recording LeRobot demonstrations

1. Press `R` to reset and randomize the objects.
2. Press `S` to start recording.
3. Place both pens and the eraser into the pencil cup.
4. Press `S` again to finish and save the episode.
5. Press `C` instead if the demonstration should be discarded.

The default dataset is written to:

```text
~/rebot-arm-dli-isaacsim/datasets/rebot_stationery_front_side
```

Each episode includes:

- `action`: six leader arm joints plus the gripper;
- `observation.state`: six B601 follower joints plus the gripper;
- `observation.images.front`;
- `observation.images.external`;
- task text: `Put the two pens and the eraser into the pencil cup`;
- episode randomization and success metadata.

The success detector requires all objects to be inside the cup, both pens to
have an inserted orientation, the gripper to be released, and object speed to
remain below `0.25 m/s` for `0.35 s`.

Visualize episode 0 with:

```bash
cd ~/rebot_lerobot
source .venv/bin/activate

lerobot-dataset-viz \
  --repo-id local/rebot_stationery_front_side \
  --root ~/rebot-arm-dli-isaacsim/datasets/rebot_stationery_front_side \
  --episode-index 0
```

## Replay

Start the Isaac receiver without opening the leader or recording:

```bash
cd ~/rebot-arm-dli-isaacsim
./run.sh --no-start-bridge --no-recording --no-dr
```

In another terminal, replay episode 0:

```bash
cd ~/rebot-arm-dli-isaacsim
~/rebot_lerobot/.venv/bin/python \
  scripts/replay_episode.py --episode 0
```

Add `--loop` for continuous playback.

## Configuration

- `config/teleop_config.json`: UDP, leader mapping, filters, and grasp assist
- `config/grasp_config.json`: scene paths, object geometry, and success criteria
- `config/domain_randomization.json`: object, lighting, camera, and recording
  randomization

The default leader-to-Isaac arm signs are:

```text
shoulder_pan  shoulder_lift  elbow_flex  wrist_flex  wrist_yaw  wrist_roll
     -1             -1            +1          +1          +1         -1
```

The calibrated leader gripper range of `0...45 degrees` maps to a simulated
range of `0...0.05 m`. Update `gripper_mapping.leader_open_deg` if the measured
leader range differs.

DevArm package (URDF + STL meshes + a structured USD authored for the
Newton/MuJoCo physics stack, MIT licensed). The teleoperation scene does not

`assets/newton_rebot_devarm/PORTING_NOTES.md` for provenance, verified facts,

pairs, units and bounds):

```bash
cd ~/rebot-arm-dli-isaacsim
"${ISAACSIM_ROOT:-$HOME/isaacsim}/python.sh" scripts/verify_newton_asset.py
```

It prints one PASS/FAIL line per check and exits non-zero on failure. Add
`--render` to also write a preview image to
`/tmp/newton_rebot_preview/newton_rebot.png` (needs the GPU).
